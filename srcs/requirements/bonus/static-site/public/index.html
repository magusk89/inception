42 School — System Administration

Inception

A complete, annotated guide to the 42 School Inception project — Docker, docker-compose, Dockerfiles, and the Makefile that ties it together. Debian-based. Includes the bonus part.

Scope of this guide. It assumes your VM is already set up and Docker is installed. It focuses entirely on the artifacts you write: Dockerfiles, docker-compose.yml, the Makefile, entrypoint scripts, and the required documentation files.

Treat every file shown here as a reference implementation to learn from — read every line, understand it, and adapt it. Submitting AI-generated files you can't explain is exactly the failure mode the subject's own AI Instructions chapter warns about.

This revision folds in every fix found while actually debugging a running deployment: the policy-rc.d stub so MariaDB's package install doesn't try to start its own daemon mid-build, /run/php and /run/mysqld created explicitly since nothing creates them without systemd, a WordPress entrypoint that checks each install step independently instead of gating everything on one file's existence, and a pinned Compose project name so fclean can actually find the volumes it's supposed to remove. The config files also carry zero comments by design, which structurally rules out one bug from this list: a stray # in a php-fpm pool file (which only recognizes ;) caused a parser failure that took a whole debugging round to track down.

What you're building

Three containers, each built from your own Dockerfile on a Debian base, talking to each other over a private Docker network, with two named volumes for persistent data, all sitting behind a single TLS entry point.

NGINX

TLSv1.2/1.3 only. The sole entry point, port 443.

WordPress + php-fpm

No nginx bundled in this container. Configured via WP-CLI.

MariaDB

No nginx bundled. Two DB users, one admin with a non-obvious name.

Architecture

All three containers share one custom bridge network. NGINX is the only container that publishes a port to the host. Internally, containers address each other by service name — Docker's embedded DNS resolves mariadb and wordpress to the right container IP automatically.

  • Only nginx publishes a portmariadb and wordpress use expose:, never ports:
  • One custom bridge network, no network: host, no --link
  • Two named volumes, pinned to /home/<login>/datavia driver_opts — never a raw bind mount under a service

Compliance checklist

Every rule from the subject, checked against the files in this guide. The compose file was run through a YAML parser and every script and Dockerfile was grepped for the forbidden patterns below before publishing this page.

Build & images

  • Each Docker image has the same name as its service — image: mariadb, image: wordpress, image: nginx
  • Each service runs in its own dedicated container
  • Base image is the penultimate stable Debian — debian:12-slim ("bookworm", now oldstable). Current stable is Debian 13 "trixie"; re-verify at debian.org/releases at build time
  • One handwritten Dockerfile per service, called from docker-compose.yml, called from the Makefile
  • No pre-built images pulled other than the Debian base
  • No :latest tag anywhere — grepped, none found

Services

  • NGINX with TLSv1.2 or TLSv1.3 only — verified in nginx.conf: ssl_protocols TLSv1.2 TLSv1.3;
  • WordPress + php-fpm installed and configured, no nginx in that container
  • MariaDB alone, no nginx in that container
  • Containers restart on crash — restart: on-failure on all three

Volumes

  • One volume for the WordPress database (db_data)
  • One volume for the WordPress site files (wp_data)
  • Both are Docker named volumes — no bind mounts under a service's volumes: key
  • Both store data inside /home/<login>/data on the host, via driver_opts

Network

  • A docker-network connects the containers — inception, driver bridge
  • No network: host, no --link, no links: — grepped, none present
  • The network line is present in docker-compose.yml
  • NGINX is the only container publishing a port, only 443

Process behaviour

  • No infinite-loop entrypoints — grepped every file for tail -f, bare bash, sleep infinity, while true: none found as actual commands, only in explanatory comments
  • Every entrypoint ends with exec into the real daemon in the foreground, so that process becomes PID 1
  • MariaDB's Dockerfile installs a policy-rc.d stub before apt-get install so the package's own postinst script can't start a second, unmanaged mysqld during the build

WordPress content

  • Two database users, one of them the administrator
  • Admin username is checked at setup time and rejects any variant of admin/administratorsee the case guard in setup_wp.sh

Secrets & config

  • No password present in any Dockerfile — grepped, none found
  • Environment variables used for configuration
  • A .env file stores the non-sensitive environment variables
  • Docker secrets store confidential information — three secrets defined and mounted
  • secrets/ and .env are gitignored — nothing sensitive committed

Documentation

  • README.md — italic first line in the exact required wording, Description, Instructions, Resources (with AI-usage note), and the four-way design comparison
  • USER_DOC.md — covers all five required end-user points
  • DEV_DOC.md — covers all four required developer points
  • Bonus services are documented in all three files — README explains what they are, USER_DOC covers how to use each one, DEV_DOC covers how to enable and manage them

Dockerfile instructions, one by one

A Dockerfile is a sequence of instructions executed top to bottom. Each one produces a cached layer; layers stack into the final image. Official reference: docs.docker.com/reference/dockerfile

InstructionPurposeNotes for this project
FROMBase image, must be firstAlways debian:12-slim, never latest — 12 ("bookworm") is the penultimate stable Debian release
RUNExecutes a command at build time, commits a layerChain installs and cleanup with && in one RUN to keep the cache effective
COPYCopies local files into the imageUsed for config files and entrypoint scripts
ADDLike COPY, plus URL fetch and tar auto-extractAvoided — prefer explicit RUN curl so the layer stays visible in history
ENVSets a variable for build and runtimeUsed for DEBIAN_FRONTEND=noninteractive so apt-get install never blocks on a prompt. Not for secrets — visible in docker inspect
ARGBuild-time-only variableCould parametrize the Debian tag via --build-arg
WORKDIRSets the working directory for later instructionsUsed in the WordPress Dockerfile: /var/www/html
EXPOSEDocuments a listening port — does not publish itActual publishing only happens for nginx, in docker-compose.yml
VOLUMEDeclares a mount pointVolumes are instead defined explicitly in compose, for host-path control
USERSwitches user for later instructionsphp-fpm and vsftpd drop privileges to www-data/a created user internally instead
CMDDefault command, overridable at docker runNot used anywhere in this project — every container's main process is fixed via ENTRYPOINT instead, deliberately, so it can't be silently replaced
ENTRYPOINTFixed executable, not easily overriddenUsed for every service. MariaDB/WordPress/FTP point at a setup script ending in exec; NGINX and Adminer, which need no setup step, use the exec-form array directly with no wrapper script at all
HEALTHCHECKPeriodic readiness probeOptional — pairs with depends_on: condition: service_healthy

The rule that matters most here: always use the exec form — ["executable", "arg"] — never the shell form. Shell form runs your process under /bin/sh -c, which becomes PID 1 instead of your actual daemon. A shell doesn't forward SIGTERM correctly, so docker stop hangs until Docker kills the container forcibly.

This is also exactly why tail -f /dev/null, bare bash, sleep infinity, and while true; do sleep 1; done are explicitly forbidden by the subject: none of them are your actual service, so the container never does real work and PID 1 never shuts down cleanly on docker stop.

A Debian-specific wrinkle: package postinst scripts (notably mariadb-server) try to start their daemon via invoke-rc.d right after installation. There's no init system running during a Docker build, so this either fails loudly or silently starts an unmanaged process baked into a layer. The fix is a one-line policy-rc.d stub that denies the start request — see the MariaDB Dockerfile below.

Multi-stage builds

Not required here since Debian's apt packages cover everything needed, but worth knowing: multiple FROM instructions let you build in one stage and copy only the compiled result into a slim final stage.

example — multi-stage pattern
FROM debian:12-slim AS builder
RUN apt-get update && apt-get install -y --no-install-recommends gcc libc6-dev \
    && rm -rf /var/lib/apt/lists/*
COPY src/ /src/
RUN gcc -o /src/myapp /src/main.c

FROM debian:12-slim
COPY --from=builder /src/myapp /usr/local/bin/myapp
CMD ["myapp"]

Compose fields, one by one

Official reference: docs.docker.com/reference/compose-file

FieldLevelPurpose
buildservicePath/context to build the image from instead of pulling one
imageserviceNames the built image — must equal the service name per the subject
container_nameserviceFixes the container's name instead of an auto-generated one
restartserviceon-failure restarts only on a crash, satisfying the subject's requirement
env_fileserviceLoads non-sensitive config from .env
secretsservice / top-levelMounts sensitive values at /run/secrets/<name>, never in env or image layers
volumesservice / top-levelNamed volumes for persistent data — no bind mounts for db/wp data
networksservice / top-levelAttaches services to the custom bridge network
portsservicePublishes to the host — only used on nginx, only 443:443
exposeserviceDocuments an internal-only port — used on mariadb (3306) and wordpress (9000)
depends_onserviceControls start order only — not actual readiness, see the callout below

depends_on is not a readiness check. It only waits for the dependency's container to start, not for the service inside it to be ready to accept connections. That's why setup_wp.sh in this guide polls MariaDB's TCP port in a loop before running any wp-cli command — without it, WordPress setup would race the database and fail intermittently.

MariaDB mandatory

Debian-only, no bundled nginx, credentials pulled from Docker secrets, and a data directory that only gets initialised once — otherwise every restart would wipe the database sitting in the named volume.

Dockerfile

srcs/requirements/mariadb/Dockerfile
FROM debian:12-slim

ENV DEBIAN_FRONTEND=noninteractive

RUN printf '#!/bin/sh\nexit 101\n' > /usr/sbin/policy-rc.d \
    && chmod +x /usr/sbin/policy-rc.d

RUN apt-get update \
    && apt-get install -y --no-install-recommends \
        mariadb-server \
        mariadb-client \
    && rm -rf /var/lib/apt/lists/*

RUN mkdir -p /run/mysqld && chown mysql:mysql /run/mysqld

COPY conf/50-server.cnf /etc/mysql/mariadb.conf.d/50-server.cnf

COPY tools/init_db.sh /usr/local/bin/init_db.sh
RUN chmod +x /usr/local/bin/init_db.sh

EXPOSE 3306

ENTRYPOINT ["/usr/local/bin/init_db.sh"]

Entrypoint script

Runs as PID 1. First run: initialises the data directory with mariadb-install-db, boots a temporary local-only instance to create the database and users from secrets, shuts it down, then execs the real mysqld (the compatibility symlink Debian's package ships for the canonical mariadbd binary). Subsequent runs: the volume already has data, so initialisation is skipped entirely.

srcs/requirements/mariadb/tools/init_db.sh
#!/bin/sh
set -e

DB_DATA_DIR="/var/lib/mysql"

DB_ROOT_PASSWORD=$(cat /run/secrets/db_root_password)
DB_PASSWORD=$(cat /run/secrets/db_password)

: "${MYSQL_DATABASE:?MYSQL_DATABASE not set}"
: "${MYSQL_USER:?MYSQL_USER not set}"

mkdir -p /run/mysqld
chown mysql:mysql /run/mysqld

if [ ! -d "${DB_DATA_DIR}/mysql" ]; then
    echo "initialising data directory"
    mariadb-install-db --user=mysql --datadir="${DB_DATA_DIR}" > /dev/null
fi

mysqld --user=mysql --datadir="${DB_DATA_DIR}" --skip-networking &
TMP_PID=$!

i=0
until mysqladmin --user=root --password="${DB_ROOT_PASSWORD}" ping >/dev/null 2>&1; do
    i=$((i + 1))
    if [ "$i" -ge 30 ]; then
        echo "bootstrap mysqld did not come up"
        exit 1
    fi
    sleep 1
done

mysql --user=root --password="${DB_ROOT_PASSWORD}" <<-EOSQL
    CREATE DATABASE IF NOT EXISTS \`${MYSQL_DATABASE}\`;
    CREATE USER IF NOT EXISTS '${MYSQL_USER}'@'%' IDENTIFIED BY '${DB_PASSWORD}';
    ALTER USER '${MYSQL_USER}'@'%' IDENTIFIED BY '${DB_PASSWORD}';
    GRANT ALL PRIVILEGES ON \`${MYSQL_DATABASE}\`.* TO '${MYSQL_USER}'@'%';
    ALTER USER 'root'@'localhost' IDENTIFIED BY '${DB_ROOT_PASSWORD}';
    FLUSH PRIVILEGES;
EOSQL

mysqladmin --user=root --password="${DB_ROOT_PASSWORD}" shutdown
wait "${TMP_PID}"

exec mysqld --user=mysql --datadir="${DB_DATA_DIR}" --bind-address=0.0.0.0

WordPress + php-fpm mandatory

Debian 12 "bookworm" ships PHP 8.2 in its default repositories, so every php-prefixed package and binary in this service is version-pinned to 8.2. php-fpm listens on TCP 9000 so NGINX (a separate container) can reach it — the default pool config only listens on a unix socket, which is unreachable across containers, so it's overridden.

Dockerfile

srcs/requirements/wordpress/Dockerfile
FROM debian:12-slim

ENV DEBIAN_FRONTEND=noninteractive

RUN apt-get update \
    && apt-get install -y --no-install-recommends \
        php8.2-fpm \
        php8.2-cli \
        php8.2-mysql \
        php8.2-curl \
        php8.2-mbstring \
        php8.2-xml \
        php8.2-zip \
        php8.2-gd \
        php8.2-intl \
        curl \
        ca-certificates \
    && rm -rf /var/lib/apt/lists/*

RUN curl -o /usr/local/bin/wp -sSL \
        https://raw.githubusercontent.com/wp-cli/builds/gh-pages/phar/wp-cli.phar \
    && chmod +x /usr/local/bin/wp

RUN mkdir -p /run/php

COPY conf/www.conf /etc/php/8.2/fpm/pool.d/www.conf

WORKDIR /var/www/html

COPY tools/setup_wp.sh /usr/local/bin/setup_wp.sh
RUN chmod +x /usr/local/bin/setup_wp.sh

EXPOSE 9000

ENTRYPOINT ["/usr/local/bin/setup_wp.sh"]

ca-certificates isn't optional here. With --no-install-recommends, Debian's curl package does not automatically pull in root certificates — the WP-CLI download over HTTPS would fail certificate verification without it. Alpine's curl package bundles this dependency by default, which is an easy thing to forget when porting a Dockerfile between distributions.

php-fpm pool config

The one line that matters: listen = 0.0.0.0:9000 instead of a socket path. The pool runs as www-data — Debian's standard web server user, created automatically by the php8.2-fpm package.

srcs/requirements/wordpress/conf/www.conf
[www]
user = www-data
group = www-data
listen = 0.0.0.0:9000
listen.owner = www-data
listen.group = www-data
pm = dynamic
pm.max_children = 5
pm.start_servers = 2
pm.min_spare_servers = 1
pm.max_spare_servers = 3
clear_env = no
catch_workers_output = yes

Entrypoint script

Polls MariaDB until it accepts TCP connections, then uses WP-CLI to download core, write wp-config.php, run the install, and create the required second (non-admin) user. The admin username is validated against the subject's naming restriction before anything is created.

srcs/requirements/wordpress/tools/setup_wp.sh
#!/bin/sh
set -e

WP_PATH="/var/www/html"

: "${DOMAIN_NAME:?DOMAIN_NAME not set}"
: "${MYSQL_DATABASE:?MYSQL_DATABASE not set}"
: "${MYSQL_USER:?MYSQL_USER not set}"
: "${WP_TITLE:?WP_TITLE not set}"

DB_PASSWORD=$(cat /run/secrets/db_password)
WP_ADMIN_USER=$(sed -n '1p' /run/secrets/credentials)
WP_ADMIN_PASS=$(sed -n '2p' /run/secrets/credentials)
WP_USER2=$(sed -n '3p' /run/secrets/credentials)
WP_USER2_PASS=$(sed -n '4p' /run/secrets/credentials)

case "$(echo "$WP_ADMIN_USER" | tr '[:upper:]' '[:lower:]')" in
    *admin*)
        echo "admin username cannot contain admin"
        exit 1
        ;;
esac

echo "waiting for database"
i=0
until php8.2 -r "exit(@fsockopen('mariadb', 3306) ? 0 : 1);" 2>/dev/null; do
    i=$((i + 1))
    if [ "$i" -ge 60 ]; then
        echo "database not reachable after 60s"
        exit 1
    fi
    sleep 1
done
echo "database reachable"

mkdir -p /run/php

cd "${WP_PATH}"

if [ ! -f "${WP_PATH}/wp-settings.php" ]; then
    echo "downloading wordpress core"
    wp core download --allow-root
fi

if [ ! -f "${WP_PATH}/wp-config.php" ]; then
    echo "writing wp-config.php"
    wp config create \
        --dbname="${MYSQL_DATABASE}" \
        --dbuser="${MYSQL_USER}" \
        --dbpass="${DB_PASSWORD}" \
        --dbhost=mariadb:3306 \
        --allow-root
fi

if ! wp core is-installed --allow-root 2>/dev/null; then
    echo "running install"
    wp core install \
        --url="https://${DOMAIN_NAME}" \
        --title="${WP_TITLE}" \
        --admin_user="${WP_ADMIN_USER}" \
        --admin_password="${WP_ADMIN_PASS}" \
        --admin_email="admin@${DOMAIN_NAME}" \
        --allow-root

    wp user create "${WP_USER2}" "editor@${DOMAIN_NAME}" \
        --role=editor \
        --user_pass="${WP_USER2_PASS}" \
        --allow-root
    echo "wordpress installed"
else
    echo "already installed"
fi

chown -R www-data:www-data "${WP_PATH}"

exec php-fpm8.2 -F -O

NGINX + TLS mandatory

The only container publishing a port. Terminates TLS 1.2/1.3 with a self-signed certificate generated at build time, then proxies PHP requests to wordpress:9000 over the Docker network.

Dockerfile

Uses ENTRYPOINT, not CMD, for the final line — unlike CMD, which anything passed after the image name at docker run time silently replaces, ENTRYPOINT can't be casually overridden. For a container whose entire job is "run nginx," that's a real, low-cost hardening: the container's one purpose stays fixed.

srcs/requirements/nginx/Dockerfile
FROM debian:12-slim

ENV DEBIAN_FRONTEND=noninteractive

RUN apt-get update \
    && apt-get install -y --no-install-recommends nginx openssl \
    && rm -rf /var/lib/apt/lists/*

RUN mkdir -p /etc/nginx/ssl \
    && openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
        -keyout /etc/nginx/ssl/inception.key \
        -out /etc/nginx/ssl/inception.crt \
        -subj "/C=PT/ST=Porto/L=Porto/O=42/CN=login.42.fr"

COPY conf/nginx.conf /etc/nginx/nginx.conf

EXPOSE 443

ENTRYPOINT ["nginx", "-g", "daemon off;"]

Note what's not here: unlike MariaDB and WordPress, there's no wrapper script ending in exec. That handoff pattern exists specifically because those two containers run setup logic — waiting for readiness, creating a database, downloading WordPress — before the real daemon can take over, so the script needs to replace itself with the daemon once setup finishes. NGINX has no such setup step: the exec-form array syntax already calls execve() directly on the nginx binary with no intermediate shell, so nginx is PID 1 immediately. There's no wrapper to hand off from, and nothing about this could move into nginx.conf either — a config file is data the already-running nginx binary reads, not a script that gets executed in its own right.

nginx.conf

Runs as www-data — Debian's conventional web server user, kept explicit here since the whole config file is overwritten by the COPY in the Dockerfile.

srcs/requirements/nginx/conf/nginx.conf
user www-data;
worker_processes auto;

events {
    worker_connections 1024;
}

http {
    include mime.types;
    default_type application/octet-stream;
    include conf.d/*.conf;
    access_log /dev/stdout;
    error_log /dev/stderr;

    server {
        listen 443 ssl;
        server_name login.42.fr;

        ssl_certificate /etc/nginx/ssl/inception.crt;
        ssl_certificate_key /etc/nginx/ssl/inception.key;
        ssl_protocols TLSv1.2 TLSv1.3;
        ssl_ciphers HIGH:!aNULL:!MD5;

        root /var/www/html;
        index index.php index.html;

        location / {
            try_files $uri $uri/ /index.php?$args;
        }

        location ~ \.php$ {
            fastcgi_pass wordpress:9000;
            fastcgi_index index.php;
            fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
            include fastcgi_params;
        }

        location ~ /\.ht {
            deny all;
        }
    }
}

The subject requires TLSv1.2 or TLSv1.3 only — the ssl_protocols line lists exactly those two and nothing older. A self-signed cert is fine for this project; your browser will warn about it once, which is expected.

access_log/error_log are set explicitly to /dev/stdout//dev/stderr. Without these two lines, Debian's packaged nginx defaults both to real files under /var/log/nginx/ — confirmed directly by running it: a genuine request and its matching error both landed in the files while docker logs stayed completely empty. The official nginx Docker image papers over this with symlinks baked into its own build; building nginx from a bare Debian base means adding these two directives yourself.

.env and secrets

Non-sensitive configuration goes in .env, loaded via env_file:. Anything confidential — passwords — goes in secrets/*.txt, referenced via the top-level secrets: block and mounted read-only at /run/secrets/<name> inside each container. Neither is committed to git.

Why secrets and not just more environment variables? Environment variables set via ENV or environment: are visible in plaintext to anyone who runs docker inspect on the container, and can leak into image layers or logs. Docker secrets are mounted as files only inside the container's filesystem, are never baked into an image layer, and don't show up in docker inspect output — which is exactly why the subject calls them out as strongly recommended for confidential information.

Makefile

Creates the host data directories the named volumes are pinned to, then delegates everything else to docker compose. Kept intentionally thin — the actual orchestration logic lives in docker-compose.yml, exactly as the subject requires.

Makefile
LOGIN := login
DATA_DIR := /home/$(LOGIN)/data
COMPOSE_DIR := srcs
PROJECT := inception
COMPOSE := docker compose -p $(PROJECT) -f $(COMPOSE_DIR)/docker-compose.yml
COMPOSE_ALL := $(COMPOSE) -f $(COMPOSE_DIR)/docker-compose.bonus.yml

all: setup up

setup:
	mkdir -p $(DATA_DIR)/db

Why down/clean/fclean reference both compose files, not just the mandatory one. Compose can only see and manage containers for services defined in whatever file(s) you actually pass it — bonus explicitly adds -f docker-compose.bonus.yml when bringing things up, but if the teardown targets only ever referenced the mandatory file, they'd be structurally blind to redis/ftp/static-site/adminer/monilite, regardless of sharing the same project name. Referencing both files unconditionally is safe even when bonus was never started — Compose simply finds nothing to do for services that don't have running containers.

The LOGIN variable at the top of the Makefile is set to the placeholder login — change it to your own 42 login, matching whatever's in docker-compose.yml's device: paths.

Why -p inception is pinned explicitly. Docker Compose derives its default project name from the working directory the command is run in — since make runs from the repo root, not from srcs/, that name depends entirely on whatever the student happens to call their cloned folder. A fclean target that guesses volume names like srcs_db_data will silently fail to remove them (the real name might be my-inception-repo_db_data instead), leaving stale volumes behind. Pinning -p inception makes the project name — and therefore every container and volume name — deterministic, and lets docker compose down -v resolve the real volume names itself instead of the Makefile guessing.

srcs/requirements/bonus/ftp/tools/init_ftp.sh
#!/bin/sh
set -e

FTP_USER=$(sed -n '1p' /run/secrets/ftp_credentials)
FTP_PASS=$(sed -n '2p' /run/secrets/ftp_credentials)

touch /etc/vsftpd.user_list

mkdir -p /var/run/vsftpd/empty
chmod 0755 /var/run/vsftpd/empty
chown root:root /var/run/vsftpd/empty

if ! id "${FTP_USER}" >/dev/null 2>&1; then
    adduser --disabled-password --gecos "" --home /var/www/html "${FTP_USER}"
    echo "${FTP_USER}:${FTP_PASS}" | chpasswd
    echo "${FTP_USER}" >> /etc/vsftpd.user_list
fi

chown -R "${FTP_USER}":"${FTP_USER}" /var/www/html

exec /usr/sbin/vsftpd /etc/vsftpd.conf
srcs/requirements/bonus/ftp/conf/vsftpd.conf
listen=YES
listen_ipv6=NO
anonymous_enable=NO
local_enable=YES
write_enable=YES
chroot_local_user=YES
allow_writeable_chroot=YES
userlist_enable=YES
userlist_file=/etc/vsftpd.user_list
userlist_deny=NO
pasv_enable=YES
pasv_min_port=21100
pasv_max_port=21110
pasv_address=127.0.0.1
seccomp_sandbox=NO
background=NO

pasv_address=127.0.0.1 is not a default — it's the fix for a classic Docker+FTP problem. Without it, vsftpd reports whatever IP getsockname() returns for the control connection, which inside a container is the container's own bridge-network address (something like 172.18.0.x) — never reachable from outside the container's network namespace. The control connection and login would work fine; any actual directory listing or file transfer, which needs a separate passive-mode data connection, would silently hang. Pointing it at 127.0.0.1 is the correct fix for testing from the VM itself, which is how this project is evaluated — it would need a real routable address to also serve genuinely external clients.

seccomp_sandbox=NO — also not optional inside a container. vsftpd installs its own internal syscall sandbox per connection via prctl(PR_SET_SECCOMP, ...) as a hardening measure, on top of whatever the OS already restricts. Docker's own default seccomp profile, applied to the container as a whole, conflicts with vsftpd trying to layer a second, nested filter on top of it — the connection gets accepted, but vsftpd's own setup step fails before it can send the normal 220 greeting, replying with a bare 500 instead. Every actively-maintained Docker vsftpd image carries this exact same line for exactly this reason.

A third fix, same root cause as /run/php and /run/mysqld. vsftpd ships its own tmpfiles.d rule — d /var/run/vsftpd/empty 0755 root root - — that only runs when systemd-tmpfiles processes it at boot. Without that directory, every connection gets accepted and then immediately rejected with 500 OOPS: vsftpd: not found: directory given in 'secure_chroot_dir':/var/run/vsftpd/empty, since that empty, root-owned jail is required for vsftpd's own privilege-separation step. Reproduced and confirmed directly: removing the directory reliably reproduces this exact error message, and creating it — with the exact permissions and ownership vsftpd's own tmpfiles.d file specifies — resolves it completely, all the way through to a successful login, upload, and directory listing.

srcs/requirements/bonus/static-site/server.js
const http = require('http');
const fs = require('fs');
const path = require('path');

const PORT = 8080;
const ROOT = path.join(__dirname, 'public');

const MIME = {
  '.html': 'text/html',
  '.css': 'text/css',
  '.js': 'application/javascript',
  '.png': 'image/png',
  '.jpg': 'image/jpeg',
  '.svg': 'image/svg+xml',
};

http.createServer((req, res) => {
  let filePath = path.join(ROOT, req.url === '/' ? 'index.html' : req.url);
  const ext = path.extname(filePath);

  fs.readFile(filePath, (err, data) => {
    if (err) {
      res.writeHead(404, { 'Content-Type': 'text/plain' });
      res.end('404 not found');
      return;
    }
    res.writeHead(200, { 'Content-Type': MIME[ext] || 'application/octet-stream' });
    res.end(data);
  });
}).listen(PORT, () => {
  console.log(`listening on port ${PORT}`);
});

## Project description: design choices

**Why Debian for the base image** — Debian was chosen over Alpine for
package maturity and glibc compatibility: MariaDB, PHP, and WP-CLI all
ship as well-tested `apt` packages with predictable version numbers.

**Virtual Machines vs Docker** — a VM virtualises an entire OS on top of
a hypervisor, which is heavy but fully isolated. A container shares the
host kernel and only packages the application plus its userspace
dependencies, which makes it far lighter and faster to start. This
project uses one VM as the host, and Docker containers inside it for
each service.

**Secrets vs Environment Variables** — environment variables are visible
in plaintext via `docker inspect` and can leak into image layers or
logs. Docker secrets are mounted as files only inside the container's
filesystem and are never baked into an image layer. This project uses
`.env` for non-sensitive configuration and Docker secrets for passwords.

**Docker Network vs Host Network** — host networking removes network
isolation entirely and every port is exposed. A custom bridge network
keeps containers isolated from the host and lets them reach each other
by service name through Docker's embedded DNS. This project uses a
single custom bridge network (`inception`) and never `network: host`.

**Docker Volumes vs Bind Mounts** — a bind mount points directly at an
arbitrary host path with no lifecycle management. A named volume is
managed by Docker end-to-end and can still be pinned to a specific host
path via `driver_opts`. This project uses two named volumes, `db_data`
and `wp_data`, both pinned to `/home/login/data/`.

build — it ships with a working value for local testing, same as the
mandatory secrets.

The bonus file also extends the existing `nginx` service rather than
adding a new one: it appends a second published port (`8443`) and
mounts `monilite.conf` into `/etc/nginx/conf.d/`, which the mandatory
`nginx.conf` already includes via `include conf.d/*.conf;` — a line
that's a no-op when that directory is empty (the default, mandatory-only
case) and picks up the extra server block only once bonus mounts a file
there. Compose appends `ports`/`volumes` entries across files by target
rather than replacing them (confirmed against Docker's own compose-file
merge documentation), so the mandatory `443:443` mapping and `wp_data`
mount on `nginx` are untouched by enabling bonus.

To manage or tear down bonus containers specifically, pass both `-f`
flags to any Compose command, since `down`/`logs`/`ps` need to know
about both files to see the bonus services:

```
docker compose -p inception -f srcs/docker-compose.yml -f srcs/docker-compose.bonus.yml down
docker compose -p inception -f srcs/docker-compose.yml -f srcs/docker-compose.bonus.yml logs -f ftp
```

Common pitfalls

1

Wrapping the main process in a shell or a loop. Breaks PID 1 signal handling and is explicitly forbidden. Always exec form, always the real daemon in the foreground.

2

Letting a Debian package's postinst script start its own daemon during the build. mariadb-server tries to start mysqld via invoke-rc.d right after apt-get install. Without the policy-rc.d stub shown in the MariaDB Dockerfile, this either fails the build or leaves a stray process baked into a layer.

3

Re-initialising the database on every restart. If the entrypoint always runs mariadb-install-db, restarting the container wipes the volume's content. Guard it with a check for existing data first.

4

Trusting depends_on for readiness. It only orders container starts. WordPress will fail intermittently against a MariaDB container that has started but hasn't finished initialising — poll for the port instead.

5

Forgetting ca-certificates on Debian. With --no-install-recommends, curl's HTTPS calls (downloading WP-CLI, Adminer) fail certificate verification unless ca-certificates is installed explicitly — Alpine's curl package pulls this in automatically, Debian's does not.

6

php-fpm's PID file directory not existing on Debian. Debian's php8.2-fpm package relies on systemd-tmpfiles to create /run/php at boot — nothing does that inside a container, so php-fpm's master process fails immediately with an "unable to create pid file" error, the container restarts in a loop, and NGINX serves a 502 because nothing is actually listening on port 9000. Symptom-wise this is easy to mistake for a networking problem; check docker logs wordpress first. Fix: mkdir -p /run/php in the Dockerfile (and again in the entrypoint as a safety net, in case the runtime clears /run between build and start).

7

MariaDB's socket directory not existing, same root cause. Debian's mariadb-server package equally relies on systemd-tmpfiles to create /run/mysqld (owned by mysql:mysql) for its socket file — without it, mysqld refuses to start at all. Since WordPress's entrypoint polls MariaDB's TCP port before continuing, the visible symptom is WordPress's log getting stuck forever on "Waiting for database...", with the site returning 403 (nothing was ever written to the shared volume) rather than 502. Same fix, different path: mkdir -p /run/mysqld && chown mysql:mysql /run/mysqld, both in the Dockerfile and as a runtime safety net in the entrypoint before the bootstrap instance starts.

8

Using # for comments in a php-fpm pool file. Unlike php.ini, which accepts both ; and #, php-fpm's pool-file parser only recognizes ;. A # comment gets read as a real config entry — and if that comment happens to contain a literal ; anywhere in its text, the parser reads up to that semicolon as an inline-comment boundary and finds a key with no value, failing with value is NULL for a ZEND_INI_PARSER_ENTRY at that exact line. php-fpm never starts, and NGINX 502s. Comments in www.conf must use ; throughout.

9

Gating the whole install block on one file's existence. If the entrypoint only checks [ ! -f wp-settings.php ] to decide "already installed," a run that downloads WordPress core successfully but then hits a transient failure later (a DB connection error, a network blip) leaves that file present — so every future restart sees it and skips setup entirely, without ever completing wp config create or wp core install. The site stays permanently half-installed. Check each step independently, and use wp core is-installed as the real completion signal rather than any single file's presence.

10

The same weak-completion-signal bug, but on MariaDB's own entrypoint. Gating the entire user/database/grant setup behind [ ! -d "$DATADIR/mysql" ] looks safe — it stops mariadb-install-db from wiping existing data — but it also means that if the grant-creation step fails for any reason on the very first boot, every restart after that sees the directory already exists and skips user creation forever, on every clean VM, identically. The visible symptom is miles away from the cause: WordPress reports Error: Database connection error (1130) Host 'x.x.x.x' is not allowed to connect even though MariaDB is up and reachable — the account genuinely doesn't exist. The fix isn't a better check, it's removing the need for one: keep mariadb-install-db one-time-gated (that part really is destructive to repeat), but make the user/grant SQL block unconditional and idempotent on every start (CREATE ... IF NOT EXISTS, re-asserted GRANT, re-asserted ALTER USER with the same password) so a partial first failure self-heals on the next restart instead of freezing into a permanently broken state.

11

php-fpm listening on a unix socket. Works fine if NGINX and php-fpm are in the same container — but the subject explicitly forbids that. Across containers, php-fpm must listen on a TCP port NGINX can reach by service name.

12

Bind-mounting the volumes directly. Writing - /home/login/data/db:/var/lib/mysql under a service's volumes: is a bind mount, which the subject forbids for these two volumes. Define them as named volumes with driver_opts pinning the host path instead.

13

Committing secrets by accident. A password that ever touches Git history counts, even if you remove it in a later commit — rewrite history or start a fresh repo if this happens. Keep secrets/ and .env in .gitignore from the very first commit.

14

Forgetting the admin username restriction. "admin123" and "Administrator-2" both still contain the forbidden substring. Validate case-insensitively against "admin" and "administrator" before creating the account.

15

Installing npm via Debian/Ubuntu's apt package. Unlike most system packages, Debian's npm depends on close to thirty separate unbundled node-* packages rather than vendoring its own dependencies — and that dependency graph is prone to failing to resolve at all (E: Unable to correct problems, you have held broken packages), independent of --no-install-recommends. If your Node.js container doesn't actually need external packages, skip npm entirely and install only nodejs. If you genuinely need packages, installing Node from the official upstream binary tarball (matching the pattern this project already uses for WP-CLI and Adminer — fetch the real artifact directly rather than trust the distro's repackaging) sidesteps the problem entirely.

16

NGINX logging to files instead of docker logs. Debian's packaged nginx defaults its access_log and error_log to real files under /var/log/nginx/ whenever a custom nginx.conf doesn't say otherwise — a container running perfectly well can still show a completely empty docker logs nginx, since every request and every error is being written INSIDE the container's filesystem instead of to its stdout/stderr. Confirmed directly: with the directives omitted, a real 502 and its matching upstream-connection error were both silently absent from the container's own output while landing correctly in the log files. The official nginx Docker image works around this with symlinks; building nginx from a bare Debian base means adding access_log /dev/stdout; and error_log /dev/stderr; explicitly.

17

Same bug, different service: php-fpm's own log also defaults to a file. Debian's packaged php-fpm.conf sets error_log = /var/log/php8.2-fpm.log by default — independent of the pool-level www.conf this project already overrides, and independent of catch_workers_output, which only controls whether worker output reaches php-fpm's own log in the first place, not where that log ends up. The fix is a single flag on the final exec: php-fpm8.2 -F -O, where -O/--force-stderr forces php-fpm's own logging to stderr even though it isn't a TTY. Worth checking for MariaDB too — but mysqld already defaults to stderr on its own when no log-error path is configured, confirmed directly rather than assumed, so no equivalent fix was needed there.

18

A bonus target that adds a second compose file, without teaching down about it. If make bonus starts services via -f docker-compose.yml -f docker-compose.bonus.yml, but down/clean/fclean only ever reference the mandatory file, those teardown targets become structurally unable to see the bonus containers at all — not a permissions issue, not a naming issue, just Compose only knowing about what it's told. Sharing the same project name doesn't help; down operates on the services defined in whatever file(s) it's given, not on "everything with this label." The fix is symmetry: reference both files in every target that manages existing containers (down, clean, fclean, and for consistency logs/ps too), while leaving up/all mandatory-only so the bonus/mandatory evaluation split the subject requires stays intact. Referencing both files is safe even when bonus was never started — Compose just finds nothing to do for services with no running containers.

19

FTP passive mode reporting an address no client outside the container can reach. Without pasv_address set, vsftpd tells the connecting client which IP to use for the data connection based on getsockname() on the control socket — inside a container, that's the container's own bridge-network IP (172.18.0.x-style), not anything published to the host. The control connection and login succeed normally, since those ride the already-established, already-forwarded connection; only the data connection — the one actually needed for a directory listing or a file transfer — tries to dial an address that doesn't exist from the client's side, and hangs. Pin pasv_address to whatever address clients will actually be connecting from: 127.0.0.1 for testing from the same VM the containers run on, a real routable address if genuinely external clients need to reach it.

20

A bare 500 where vsftpd's 220 greeting should be. vsftpd installs its own per-connection syscall sandbox via prctl(PR_SET_SECCOMP, ...), layered on top of whatever the OS already restricts. Docker's own default seccomp profile on the container conflicts with vsftpd trying to nest a second filter inside it — the TCP connection is accepted, but vsftpd's internal sandbox setup fails before it can even send the greeting, so the client sees a bare 500 instead of the expected 220. Confirmed directly: the exact same config, user setup, and connection sequence worked flawlessly when vsftpd ran directly on a bare host, and every actively-maintained Docker vsftpd image out there carries the same one-line fix — seccomp_sandbox=NO — for exactly this reason.

21

A second, different 500 hiding right behind the first one. Fixing the seccomp issue above surfaces a genuinely separate failure: 500 OOPS: vsftpd: not found: directory given in 'secure_chroot_dir':/var/run/vsftpd/empty — the exact same class of bug as /run/php and /run/mysqld earlier in this list, just a third daemon with its own tmpfiles.d rule that only fires under systemd-tmpfiles. Worth internalizing as a general check, not just three isolated fixes: any Debian-packaged daemon might have a file under /usr/lib/tmpfiles.d/<name>.conf specifying a runtime directory it expects to already exist — dpkg -L <package> | grep tmpfiles or a direct look in that directory catches this before it costs a debugging round instead of after.
